# 我们的宇宙：AI 开发与验收流程

本流程参考“开饭开拍”的任务记录模式，并按“我们的宇宙”的 WebGL、Blender、资产版权和本地照片存储特点做了调整。本仓库只面向桌面 Web；不开发、验收或发布移动端和微信小程序。Codex 与 Grok Build 的角色、状态和交接格式以 [联合开发工作流](CODEX_GROK_WORKFLOW.md) 为准。

## 1. 任务等级

### G0：文档或纯视觉调整

同时满足以下条件：

- 只修改文档、普通文案、注释或纯 CSS 视觉参数；
- 不改变事件、导航、数据、权限、依赖和渲染算法；
- 不影响本地音乐存储、渲染生命周期和桌面 Web 行为。

执行路线：单代理直接实现、自查并说明结果。通常不创建任务记录。

### G1：普通功能开发

适用于普通页面交互、组件、工具函数、测试、局部性能优化和低风险缺陷修复。

- 小任务直做：最多修改 2 个既有业务文件，不新增协议、依赖、持久化字段或跨页状态。
- 标准任务：修改 3–7 个业务文件、新增普通组件，或需要回归多个相邻交互。

G1 标准任务必须创建 `docs/tasks/YYYY-MM-DD-short-name.md`。默认路线为 Codex 写规格、Grok Build 实现与自测、Codex 独立验收。

### C1：高风险变更

命中任一条件即为 C1：

- 修改 IndexedDB 本地音乐存储或浏览器持久化结构；
- 修改云同步、上传、分享、鉴权、隐私或外部 API；
- 修改 WebGL/Canvas 核心渲染架构、资源生命周期或跨端渲染协议；
- 修改生产依赖、锁文件或 Vite 项目配置；
- 一次预计修改 8 个以上现有业务文件；
- 可能造成本地音乐丢失、覆盖或无法恢复。

执行路线：Codex 先完成方案与兼容评审，明确允许/禁止范围和测试矩阵；Grok Build 做最小实现；Codex 最后独立读取 diff 并验收。

### C2：关键架构或事故处理

适用于数据丢失、安全事件、不可逆迁移、核心跨端架构重做，或同一缺陷两轮修复仍未通过验收。

执行路线：由 Codex 主导诊断和关键实现；Grok Build 只承担已隔离的低风险配套；必须给出回滚、兼容和人工验证方案。

## 2. 每个任务的固定流程

1. Codex 自动分类并完成开工检查：阅读 README、PRD、相关实现和测试，检查 `git status --short --branch`，保护已有改动。
2. Codex 写任务规格：明确目标、非目标、影响范围、验收标准、异常场景；C1/C2 同时完成前置评审。
3. 用户确认必要的产品选择、外部资产、依赖安装、数据操作或发布动作。
4. 当前写入者做最小实现：不做任务外重构；组件、工具函数和渲染引擎遵守文件规模限制。
5. 实现者填写 C 节并停止写入，状态改为 `waiting_codex_review`；“实现完成”不等于“验收通过”。
6. Codex 独立读取实际 diff、新文件和未跟踪文件，重新运行测试、类型检查、生产构建和浏览器验收。
7. Codex 在 D 节给出唯一结论；需要返修时只列最小范围，同一问题最多两轮，之后升级 C2。
8. 验收通过后才进入下一任务；提交、推送和部署仍需用户明确授权。

## 3. 项目专用验证门禁

普通代码任务至少执行：

```powershell
npm run typecheck
npm test
git diff --check
git status --short
```

涉及 Web 页面或 Three.js 时增加：

```powershell
npm run build
```

并在浏览器中检查实际画面、交互、空状态、缩放和资源释放。

不为新任务开发移动端或微信小程序。

## 4. 强制质量边界

- React 页面/业务组件不超过 300 行，超过 220 行应主动评估拆分。
- 通用工具函数文件不超过 200 行。
- Canvas/WebGL 渲染引擎文件不超过 400 行。
- 单个函数原则上不超过 60 行；不同变化原因必须拆分。
- 不得删除测试来换取通过，不得用历史测试数字冒充本次结果。
- 不得把密钥、令牌、临时访问 URL、个人照片或个人信息写入仓库。
- 未经用户明确授权，不执行部署、提交、推送、发布、发布或真实数据迁移。
- 联合任务每轮只有一个写入者；Codex 验收期间 Grok Build 必须停止修改，Grok Build 实现期间 Codex 不修改同一任务文件或业务文件。

## 5. 任务记录规则

- G1 标准、C1、C2 使用一个任务文件作为单一事实来源。
- 文件名：`docs/tasks/YYYY-MM-DD-short-name.md`。
- 同一文件持续记录规格、实现、测试、验收和返修，不重复创建多个交接文档。
- 交接只给结论和证据，不粘贴完整终端日志。
- 同一问题最多进行两轮定向返修；仍失败则升级为 C2。
- 统一状态为 `draft → ready_for_review → approved_for_implementation → implementing → waiting_codex_review → accepted / changes_requested / blocked`。

任务模板见 [AI_TASK_TEMPLATE.md](AI_TASK_TEMPLATE.md)，角色分工与一键交接文本见 [CODEX_GROK_WORKFLOW.md](CODEX_GROK_WORKFLOW.md)。
