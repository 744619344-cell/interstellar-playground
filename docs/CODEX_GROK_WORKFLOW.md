# Codex × Grok Build 联合开发工作流

> 参考“开饭开拍”的单任务文档、前置评审、结构化交接和独立验收模式，按本桌面 Web 项目的 WebGL、Blender、资产版权和本地数据边界适配。

## 1. 角色分工

| 阶段 | Codex | Grok Build | 用户 |
| --- | --- | --- | --- |
| 需求澄清 | 主责，形成可验收目标 | 提供实现可行性补充 | 确认重大产品选择 |
| 任务分级 | 主责 | 不自行降级 | 可调整优先级 |
| C1/C2 前审 | 主责，写允许/禁止范围 | 阅读并指出阻断 | 确认外部操作和重大扩展 |
| 实现 | 架构核心或明确保留 | 默认主实现者 | 观察阶段结果 |
| 自测 | 检查自己的核心改动 | 主责，填写精确结果 | 必要时视觉确认 |
| 最终验收 | 独立读取 diff 并重跑验证 | 停止写入，等待结论 | 接受最终结果 |
| 返修 | 给出最小返修指令 | 按指令返修并重新交接 | 第二轮失败时确认升级方案 |
| Git/发布 | 未授权不执行 | 未授权不执行 | 明确授权提交、推送或部署 |

## 2. 单一事实来源

G1 标准、C1、C2 必须先创建一个任务文件：

```text
docs/tasks/YYYY-MM-DD-short-name.md
```

同一个文件连续填写：

- A：需求与验收标准。
- B：Codex 前置评审。
- C：Grok Build 或 Codex 的实现交接。
- D：Codex 最终验收与返修结论。
- E：面向用户的完成说明。

禁止为同一轮实现重复创建“交接版”“最终版”“复验版”任务文档。

## 3. 任务分级与执行路线

### G0：独立任务

纯文档、注释、非交互文案或低风险 CSS。单代理实现并自查，不强制联合。

### G1 小任务：直做

最多两个既有业务文件，不涉及协议、存档、依赖、WebGL 生命周期或资产替换。Codex 或 Grok Build 任一方完成并自验收。

### G1 标准联合

适用于 3–7 个文件、普通组件、局部交互或多个相邻回归点：

```text
Codex 写规格 → Grok Build 实现与自测 → Codex 最终验收
```

### C1：高风险联合

命中核心 WebGL 架构、资源生命周期、坐标系统、骨架/动画资产、存档、依赖、音频或 8 个以上业务文件：

```text
Codex 前置评审
→ 用户确认必要的产品/外部操作
→ Grok Build 在白名单范围实现
→ Codex 独立重跑测试与实际行为验收
→ 通过或最小返修
```

### C2：Codex 主导

数据损坏、安全事件、不可逆迁移、核心架构事故，或同一问题两轮返修仍失败。Codex 主导诊断和关键实现；Grok Build 不得自行扩大范围。

## 4. 文件所有权与并发规则

联合开发不等于同时编辑同一工作区：

1. 每轮只有一位写入者。
2. 任务文档 B 节列出允许修改的文件或目录。
3. 写入者完成后更新 C 节并停止修改。
4. 验收者先读取实际 `git diff` 和未跟踪文件，再运行检查。
5. 验收期间只有 Codex 可以写 D 节；发现问题时不顺手重构。
6. Grok Build 收到返修指令后才恢复写入。
7. 用户的新需求若改变任务目标，停止当前任务并先更新 A/B 节。

如果必须并行，只能拆成没有共享文件、没有共享接口变更的独立任务，并分别拥有任务文档。默认不并行。

## 5. 标准流程

### Step 1：Codex 开工检查

- 读取 README、PRD、架构、当前任务和相关代码。
- 执行 `git status --short --branch`，识别任务外既有改动。
- 确认当前开发服务器、构建产物和未跟踪资产不会被覆盖。
- 填写任务 A 节；C1/C2 同时填写 B 节。

### Step 2：用户确认

以下情况必须由用户确认后才能继续：

- 产品方向存在会显著改变结果的选择。
- 下载、购买、许可或替换外部模型/音乐。
- 安装依赖、使用 Blender 生成正式资产。
- 提交、推送、部署或发布。
- 需要覆盖、删除或迁移现有数据。
- 即将进入 Blender 建模、拓扑与权重、骨骼绑定、动作制作/修复、复杂着色器或高难度 3D 架构时，先提醒用户切换到 GPT-6，并等待用户确认后开工。

### Step 3：交给 Grok Build

Codex 给出一键复制指令，必须包含：任务文件、等级、已完成内容、允许/禁止范围、验收标准、必跑测试、停止条件和交回对象。

### Step 4：Grok Build 实现

- 先复述任务边界并读取实际 Git 状态。
- 仅修改白名单文件。
- 新增测试并运行本轮命令。
- 检查 diff、未跟踪文件、文件规模和敏感信息。
- 填写任务 C 节，输出结构化交接，不提交、不推送。

### Step 5：Codex 独立验收

- 不把 Grok 的摘要或测试数字视为证据。
- 读取真实 diff、新文件和未跟踪文件。
- 对照 A/B 节逐项检查行为、兼容、失败恢复和资源释放。
- 独立重跑测试、构建和浏览器/Blender 视觉验收。
- 只在 D 节写：阻断问题、重要问题、一般建议和唯一结论。

### Step 6：返修或完成

- 最多两轮定向返修。
- 返修只处理 D 节失败项，不接受顺手优化。
- 第二轮仍失败，升级 C2，由 Codex 重新诊断。
- 验收通过后才允许进入路线图下一任务。

## 6. 项目专用验证矩阵

普通代码：

```powershell
npm run typecheck
npm test
git diff --check
git status --short --branch
```

Web/Three.js 增加：

```powershell
npm run build
```

并检查实际浏览器画面、输入、暂停、恢复、刷新、控制台、资源释放和目标视口。微信小程序不属于新功能门禁。

Blender/GLB 任务增加：

- glTF Validator。
- 三角面、骨骼、动作名、纹理、尺寸清单。
- 正面、侧面、背面动作预览。
- Three.js 独立查看器与项目实际场景。
- 任何抱胸、手指变形、背包扭曲、陷地或滑步均返修。

音频任务增加：

- 授权清单和生产构建许可。
- 用户手势解锁、隐藏暂停、淡入淡出和内存检查。
- 未授权《星际穿越》原声不得进入仓库或构建。

## 7. 状态定义

```text
draft
→ ready_for_review
→ approved_for_implementation
→ implementing
→ waiting_codex_review
→ accepted | changes_requested | blocked
```

`waiting_codex_review` 不能对用户表述为“任务已通过”。

## 8. Git 和外部操作边界

- 默认共享当前工作区，不自动创建或切换分支。
- 开工时记录基线，但不清理 dirty worktree。
- 未经用户明确授权，两位代理都不得提交、推送、部署或发布。
- 不使用 `git reset --hard`、`git checkout --` 或清理未跟踪文件。
- 外部模型、音乐和纹理在进入仓库前必须完成许可与资产清单。
- 本机临时路径、账号、密钥和私人文件不进入任务文档。

## 9. 自动化边界

当前采用人工确认和一键复制交接，不自动启动 Grok Build，也不自动把其完成状态视为验收通过。

如后续需要自动流水线，应单独创建 C1 任务实现：任务哈希确认、固定仓库、单实例锁、结构化交接、日志脱敏、无 shell 子进程和失败不假成功。不得直接复制另一项目的 token、通知地址、运行目录或远程接入配置。

## 10. 一键交接模板

### Codex → Grok Build

```text
请 Grok Build 开始实现：<任务名>
任务文档：<docs/tasks/...md>
等级/路线：<G1 标准联合 / C1 / C2 配套>

Codex 已完成：<需求规格、前置评审、架构边界>
你需要完成：<明确且可验证的剩余工作>

允许修改：
- <文件或目录>

禁止修改：
- <协议、数据、依赖、旧代码、外部操作>

验收标准：
- <逐项结果>

必须执行：
- npm run typecheck
- npm test
- npm run build（涉及 Web/Three.js 时）
- git diff --check
- git status --short --branch

停止条件：<需要用户确认或会扩大范围的情况>
完成后：填写任务文档 C 节，停止写入，并把结构化交接发给 Codex。不要提交、推送或部署。
```

### Grok Build → Codex

```text
请 Codex 验收：<任务名>
任务文档：<docs/tasks/...md>
等级/路线：<等级与路线>
实现状态：<已完成 / 部分完成 / 阻塞>
主要修改：<文件和用户可见行为>
测试：<命令与精确通过/失败数量>
兼容与风险：<结论>
明确未做：<提交、推送、部署、外部操作>
重点验收：<1–3 个最重要检查点>
```

### Codex → Grok Build 返修

```text
请 Grok Build 最小返修：<任务名>
任务文档：<docs/tasks/...md>
验收结论：<修改后复验 / 不通过>
返修轮次：<1/2 或 2/2>
问题与证据：<复现、文件、行号或测试>
允许修改：<最小范围>
禁止事项：<不可扩大范围>
必须验证：<命令和实际行为>
完成后：更新 C 节返修记录并重新交给 Codex，不要提交、推送或部署。
```
